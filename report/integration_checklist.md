# Integration Checklist
### What an organisation needs to fully integrate the `pay` Flutter package

> **Scope:** Physical goods and services only. For digital/virtual goods, Apple Pay and Google Pay are prohibited by platform policy — see [`policy_compliance.md`](./policy_compliance.md).

---

## 1. Apple Pay

### Account & Enrollment
- [ ] Active Apple Developer Program membership ($99/year)
- [ ] Enrolled as an individual or organisation — note: organisation enrollment requires a D-U-N-S number (allow 2–5 business days for verification)

### Merchant Identity
- [ ] Merchant ID created in the [Apple Developer Portal](https://developer.apple.com/account/resources/identifiers/list/merchant) — format: `merchant.com.yourcompany.appname`
- [ ] Payment processing certificate generated — requires a Certificate Signing Request (CSR) from your payment processor (e.g. Stripe, Adyen)
- [ ] Merchant identity certificate registered (used for session validation if implementing on web; apps use the processing certificate only)

### Xcode Project
- [ ] Apple Pay capability enabled in Xcode under *Signing & Capabilities*
- [ ] Merchant ID added to the entitlements — Xcode adds this automatically when the capability is enabled
- [ ] Bundle ID matches the one registered in the Developer Portal
- [ ] Correct provisioning profile selected (must include Apple Pay entitlement)

### Configuration (in-app)
- [ ] `merchantIdentifier` matches the Merchant ID created above
- [ ] `merchantCapabilities` declared (`3DS` required; `debit` and `credit` as appropriate)
- [ ] `supportedNetworks` declared (`visa`, `masterCard`, `amex`, `discover` — include only what your processor supports)
- [ ] `countryCode` and `currencyCode` set correctly for your market
- [ ] `requiredBillingContactFields` and `requiredShippingContactFields` scoped to only what you actually need (requesting unnecessary data fails Apple review)
- [ ] `displayName` set to a recognisable business name (shown on the payment sheet)

### Testing
- [ ] At least one test card added to the Wallet on a physical device or iOS Simulator (Simulator > Features > Add Wallet Card)
- [ ] Payment flow tested end-to-end in the sandbox environment
- [ ] Declined-card and cancel scenarios tested

## 2. Google Pay

### Account & Enrollment
- [ ] Google account with access to the [Google Pay & Wallet Console](https://pay.google.com/business/console)
- [ ] Business profile completed and approved
- [ ] Merchant ID obtained from the Console

### Integration Configuration
- [ ] `environment` set to `TEST` during development; must be changed to `PRODUCTION` before launch
- [ ] `merchantName` set to your registered business name
- [ ] Payment gateway configured — either `gateway` (recommended; e.g. Stripe, Adyen) or `DIRECT` (requires PCI DSS SAQ D compliance)
- [ ] `gatewayMerchantId` set to your merchant ID with the chosen gateway
- [ ] `allowedCardNetworks` and `allowedAuthMethods` scoped to what your processor accepts
- [ ] `transactionInfo.countryCode` and `currencyCode` correct for your market
- [ ] Billing address fields requested only if genuinely required

### Production Approval
- [ ] Integration reviewed and approved by Google before switching to `PRODUCTION` — submit via the [Google Pay & Wallet Console](https://pay.google.com/business/console)
- [ ] Google Pay brand guidelines followed in the UI (button size, placement, do-not-alter rules) — violations can block approval
- [ ] Production approval typically takes 1–5 business days

### Android Build Requirements
- [ ] `minSdkVersion` set to **23** or higher in `android/app/build.gradle` (Google Pay SDK recommendation)
- [ ] `compileSdkVersion` set to **34** or higher

### Distribution
- [ ] App will be distributed through the **Google Play Store** — Google Pay in production does not work in sideloaded APKs

### Testing
- [ ] Test account with a saved card on the Android device or emulator
- [ ] `TEST` environment confirmed active during development (no real charges)
- [ ] Note: in `TEST` mode, `userCanPay` always returns `true` and the token is always `"examplePaymentMethodToken"` — do not rely on these for production gating logic
- [ ] Cancel and error flows tested

## 3. Payment Processor

> The `pay` package hands you a payment token. You must send that token to a backend that charges it through a payment processor. Nothing is charged without this step.

### Account Setup
- [ ] Account created and verified with chosen processor (e.g. [Stripe](https://stripe.com), Adyen, Braintree)
- [ ] KYC (Know Your Customer) documentation submitted and approved — required before live payments are enabled
- [ ] Bank account linked for payouts
- [ ] Business details, registered address, and tax information provided

### Apple Pay — Processor Side
- [ ] Apple Pay enabled in the processor dashboard
- [ ] Payment processing certificate CSR generated by the processor and uploaded to the Apple Developer Portal
- [ ] Certificate expiry date noted — Apple Pay certificates expire every 25 months and must be renewed

### Google Pay — Processor Side
- [ ] Google Pay enabled in the processor dashboard
- [ ] Gateway name and gateway merchant ID confirmed (used in the Google Pay configuration JSON)

### API Keys
- [ ] Test (sandbox) secret key obtained and stored securely
- [ ] Live (production) secret key obtained — kept only in backend environment variables, never in the app
- [ ] Key rotation policy in place

## 4. Backend Server

### Infrastructure
- [ ] Server reachable over **HTTPS** — both Apple and Google require TLS; HTTP is rejected
- [ ] Valid TLS certificate (e.g. via Let's Encrypt or your hosting provider)
- [ ] Environment variables used for all secrets — never hardcoded

### Payment Endpoint
- [ ] `POST /payments/process` endpoint (or equivalent) accepts the token, amount, and description
- [ ] Token submitted to the processor to create a PaymentIntent / charge
- [ ] Response returns success/failure status to the app
- [ ] Request validation in place (reject malformed or missing fields)

### Reliability
- [ ] Idempotency keys used when creating charges — prevents duplicate charges if the client retries
- [ ] Webhook endpoint configured to receive async payment events from the processor (e.g. `payment_intent.succeeded`, `payment_intent.payment_failed`)
- [ ] Webhook signature verification enabled — prevents spoofed events
- [ ] Failed payment events handled (notify user, flag order)

### Observability
- [ ] Structured logging for all payment attempts (do not log full card numbers or tokens)
- [ ] Error alerting configured
- [ ] Payment processor dashboard monitored for disputes and refunds

## 5. Flutter App

### Package
- [ ] `pay` package added to `pubspec.yaml` at the required version
- [ ] `flutter pub get` run successfully
- [ ] Native platform dependencies resolved (no build errors on iOS and Android)

### Implementation
- [ ] `PaymentConfiguration` built from a valid JSON string for each provider
- [ ] `PaymentItem` list built correctly — total item must be the last entry and labelled `total`
- [ ] `PaymentItem.amount` uses a period as the decimal separator regardless of device locale (e.g. `"12.99"` not `"12,99"`)
- [ ] `ApplePayButton` used on iOS; `GooglePayButton` used on Android — platform policy requires using the official branded buttons, not custom button widgets
- [ ] `onPaymentResult` sends the token to the backend — token is never charged client-side
- [ ] `onError` handles `paymentCanceled` silently (user dismissed the sheet — not an error); all other codes shown to the user
- [ ] `childOnError` widget set if you want to show a fallback when the user cannot pay (e.g. no cards in Wallet)
- [ ] Loading/processing state shown while the backend responds
- [ ] Success state navigates away or confirms the order
- [ ] Payment items rebuilt on every state change (quantity, variant selection) so the sheet always shows the correct amount
- [ ] Payment configuration JSON is fetched from the backend rather than hardcoded in the app (recommended — allows updates without an app release)

### Platform Configuration
- [ ] iOS: Merchant ID in entitlements matches the one in the `PaymentConfiguration` JSON
- [ ] Android: No additional native configuration required for `TEST` mode; production requires the approved merchant ID

## 6. Legal & Compliance

### Required Policies
- [ ] **Privacy Policy** — required by both Apple App Store and Google Play; must describe what payment data is collected and how it is handled
- [ ] **Terms & Conditions** — covering purchase terms, refunds, and cancellations
- [ ] **Refund Policy** — clearly stated; Apple and Google both require a published policy before approving commerce apps

### Data & Security
- [ ] PCI DSS compliance confirmed — when using a gateway like Stripe, the processor handles cardholder data and the organisation qualifies under SAQ A (reduced scope); document this
- [ ] GDPR / relevant data protection law compliance confirmed for your jurisdiction
- [ ] No raw card numbers, CVVs, or full payment tokens logged or stored by the application or backend
- [ ] Data retention policy defined for order and payment records

### Platform Review Readiness
- [ ] App Store: App does not sell digital goods, in-app currency, or subscriptions through Apple Pay (must use StoreKit/IAP for those)
- [ ] Google Play: App does not sell digital goods through Google Pay (must use Play Billing for those)
- [ ] Use case clearly identifiable as physical goods or services consumed outside the app

## 7. Testing Checklist

| Scenario | Apple Pay | Google Pay |
|---|---|---|
| Successful payment — single item | ☐ | ☐ |
| Successful payment — multiple quantity | ☐ | ☐ |
| User cancels the payment sheet | ☐ | ☐ |
| Payment declined by issuer | ☐ | ☐ |
| Network error during backend call | ☐ | ☐ |
| Backend returns an error | ☐ | ☐ |
| Incorrect total amount | ☐ | ☐ |
| Device has no saved cards | ☐ | ☐ |

---

## 8. Production Launch

- [ ] `environment` in Google Pay configuration changed from `TEST` to `PRODUCTION`
- [ ] Google Pay production integration approved via the Console
- [ ] Live Stripe (or processor) secret key deployed to the production server
- [ ] Apple Pay tested on a real device with a real card in the production environment
- [ ] Webhook endpoints live, verified, and monitored
- [ ] Apple Pay certificate expiry date calendared for renewal
- [ ] Smoke test on production with a real low-value transaction before full launch

---

## Summary

| Area | Minimum time to be ready |
|---|---|
| Apple Developer enrollment (organisation) | 2–5 business days (D-U-N-S verification) |
| Payment processor KYC approval | 1–3 business days |
| Apple Pay certificate setup | Same day once enrolled |
| Google Pay production approval | 1–5 business days |
| Backend development | Depends on team; basic endpoint is a few hours |
| Full end-to-end testing | 1–2 days |

> **The most common blockers** are D-U-N-S verification for Apple Developer enrollment, KYC delays with the payment processor, and Google Pay production approval. Plan for up to two weeks from start to production-ready if none of these are already in place.
